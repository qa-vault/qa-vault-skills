# Maintain Test Cases

## Overview

A **change-driven sync**: development changed the product, so part of the QA Vault repository is now stale. Bring it back in line in **one coherent, reviewed changeset** — updates, new cases and removals together — that the engineer reviews as diffs on the web Review page and applies there.

## The process: explore → find → compose → validate → stage → hand over → act on feedback

Like `create-test-cases`, you do **not** write to the vault: the changes are staged as a **changeset** the engineer reviews on the web Review page, with a diff per case, and applies there. The protocol — summary, hand-over, feedback loop, when you may decide or apply, the one direct-write exception — is in `create-test-cases` (*The changeset lifecycle*, *Summary*, *When the person asks for a direct write*); this skill adds what maintenance stages.

1. **Explore the change** from any source you can read — a diff, PR, ticket/spec, a prose description, or the existing cases themselves. Understand what actually changed well enough to know what to look for. If the change is described too thinly, ask. Read the project's rules and lessons (`get_project_rules`, `get_project_lessons`). While exploring, note anything suspicious as you pass it (see *Validation: flag suspicious behavior* below) — you'll sweep for these before staging.
2. **Find affected cases.** Search **broadly** — a change usually ripples past the obvious area (a new 2FA login step also touches password-reset, remember-me, and any case asserting "reaches the dashboard"). Use semantic **and** title search to gather candidates (see the `search-test-cases` modes), phrasing each semantic query as a full description of the behaviour rather than a couple of keywords. Then `get_test_case` each candidate and **judge affectedness from its actual `steps` and descriptive fields (`description`, `preconditions`) — not its title.** A title like "User logs in" won't mention the changed step, so a title-only scan silently drops cases whose steps do reference it. Never edit **or dismiss** a case you haven't read in full. A case whose `open_changesets` is not empty is already being proposed on: say so and ask whether to continue there instead of opening a second proposal.

   Breadth here is a completeness claim, so treat the response's own accounting as part of the search: a listing that reports a `total_count` above what it returned is one page of several — page it out with `offset` before concluding. Don't cap a semantic search with `limit`; the server already returns everything it judged relevant, and a cap can only hide matches. A missed case here doesn't fail loudly — it ships as an approved expected result that no longer matches the product.
3. **Compose the changeset** — per affected case its **final state** (the whole case, every field, not a patch), per obsolete case the removal, per gap the new case; and for each a `change_note` saying what changed in the product and what is edited here, or why the case is obsolete. Then the **validation sweep**: re-read the set against what the change actually does; write a flag for entries whose implemented behavior you noted as suspicious; check across entries for inconsistencies (two screens now handling the same situation differently). See *Validation: flag suspicious behavior*.
4. **Stage.** `create_changeset` (title names the change; `summary` per the *Summary* recipe, with the *Dedupe* part replaced by **Affected** — what you searched and which cases you judged affected or not, and why). Then `stage_changeset_items` with the items of *The three kinds of item* below — one call for everything (split only where the tool’s item limit forces it), never one per case; when a new case needs a new suite, stage the suite in a call of its own first and point the case at its `item_id`, as `create-test-cases` step 5 does. A refusal names the field; fix and stage again.
5. **Hand over.** The `review_url`, the counts (updated / new / removed), the validation summary and the general observations — then stop; do not offer to apply. The engineer sees each update as a diff on the Review page.
6. **Act on feedback, report when it lands** — exactly as `create-test-cases` steps 7 and 8: `get_changeset` first; re-stage the addressed items with `item_id` + `expected_revision` as whole items (payload, `suite_ref`, `change_note`, unresolved flags) and resolve each comment with a note (a question-only comment is answered in the note, item untouched); feedback given in chat is recorded with `add_changeset_comment` before you act (no items when it concerns the whole changeset) and resolved after; re-read `get_changeset` before handing over again; feedback given in chat is recorded with `add_changeset_comment` before you act and resolved after; never re-stage an item nobody asked about; after an apply, report updated / deprecated / created / deleted by `#number "title"`, and run `backfill_embeddings` when the response lists `embedding.failed`.

## The three kinds of item

- **Update / extend** a stale case — what goes into the case is the change in **behaviour**; a change in presentation alone (restyle, new icon, colour, animation, a control moved) makes no case stale unless the case asserts that presentation; such a case is updated by rewriting those sentences as the outcome they signal (the redesign test), never by describing the new look. The edited expected results pass the redesign test of `create-test-cases` (*Fields to set on every case* → `steps`). An `update_case` item: `case_id`, `change_note`, and the **whole** case in `payload` as it should read after the update (title, description, preconditions, postconditions, priority, severity, type, layer, behavior, automation_ref, tags, steps, search_abstract). Apply overwrites the case in full, so a field you leave out is a field you cleared — start from `get_test_case` and change only what the product change requires. Two fields are the exception: `status` and `automation` keep their stored value when the payload omits them, so send `status` only to change it (see *Remove obsolete*) and `automation` never (see *Preserve automation status*). `tags` is the full intended list. When the edit changes **what the case verifies**, regenerate `search_abstract` in the same payload (format and rules in `create-test-cases`) — one describing the old behavior keeps matching queries the case no longer answers. Leave `suite_ref` out to keep the case where it is; set it only to move the case. If maintenance reveals **mass** abstract absence across a project, that is not this skill's job — hand it to `backfill-search-abstracts`.
- **Author net-new** cases for behavior the change introduces that nothing covers yet (e.g. wrong / expired / resend-code screens for new 2FA) — `create_case` items **following `create-test-cases`**: grounded in the project docs + the actual new implementation (real labels/flows, not invented), same required-field model (`title`, `description`, `preconditions` if non-obvious, UI-verifiable `steps`, `priority`, `behavior`, `automation: not_automated`, high-level reuse-first `tags`, `search_abstract`); no `severity`/`type`/`layer`/`postconditions` unless asked; a `change_note` saying which change made the case necessary.
- **Remove obsolete** cases — a `delete_case` item with `case_id`, an empty `payload: {}` and a `change_note` giving the reason (the feature it tested is gone). That is the default: a case whose only subject is gone is removed, not rewritten into something else — a rewrite of a different scenario is a new case plus a removal. When the engineer would rather keep history, stage an `update_case` item instead whose payload is the current case with `"status": "deprecated"` and a `change_note` saying so — a deprecated case stays readable, a deleted one is gone. The status carries the deprecation; do not write "DEPRECATED" into the title or description.

```json
{ "kind": "update_case", "case_id": 418, "change_note": "Login now asks for a 6-digit email code after the password; the dashboard step moves behind it.", "payload": { "title": "...", "...": "...", "steps": [ ... ], "search_abstract": "..." } }
{ "kind": "delete_case", "case_id": 421, "payload": {}, "change_note": "The 'login without 2FA' path no longer exists; the case only tested it." }
```

## Validation: flag suspicious behavior

The changed implementation **may itself contain bugs** — maintenance runs right after development changed the product, usually before anyone has manually explored it, so you are the first pair of eyes. Flag **implemented, verifiable behavior a competent QA engineer would pause at**: inconsistent behavior between screens/flows; silent data loss or truncation; missing loading/empty/error states; destructive actions without confirmation; misleading labels; dead-end flows. You are not claiming "bug"; you are saying "confirm this is intended before it becomes the approved expected result." Maintenance adds two signals of its own:

- **The change contradicts a previously approved expected result.** An existing case's expected behavior was approved truth; when the new implementation does something surprisingly different or worse, that may be a regression, not a redesign — flag the `update_case` item instead of silently rewriting the case.
- **A "gone" feature may be breakage, not removal.** Before staging a `delete_case`, check the disappearance is plausibly intended (the ticket/diff says so); if it looks accidental, flag it.

**Keep flags few and high-signal**: each names a concrete observed behavior and why it's suspicious — no style opinions, no speculation. "The devs confirmed it's final" or "the engineer is in a hurry" is never a reason to skip a flag — deciding is the engineer's job, noticing is yours. A flagged entry still describes the **implemented** behavior (code wins) until the engineer rules otherwise. Each flag goes on its item as one string in `flags` — `"<observed behavior> — <why it looks suspicious>"` — and is repeated in the summary's *Flagged* part; the case text carries no trace of it. The Review page blocks approval of a flagged item until the engineer resolves the flag.

## Preserve automation status

A case's `automation` value (`not_automated` / `to_be_automated` / `automated`) reflects engineering reality you can't see from here. **Never silently change it.** Leave `automation` **out** of every `update_case` payload: apply keeps the stored value when the field is absent — it is one of the two fields not cleared by omission. When you edit an already-`automated` case, **flag the item**: a redesign can break the existing automated test's locators even when behavior is unchanged, so the engineer should confirm whether it still passes. When such a case has an `automation_ref`, name it in the flag — that is the spec whose locators may now be stale; healing it is `heal-automated-tests`' job, not this skill's. Send `automation` only on the engineer's explicit instruction to change it.

## Discipline

Search broadly before deciding; read before editing; stage the whole changeset for review before anything is written; surface scope ambiguity instead of guessing; decide, apply or discard over MCP only on the engineer's explicit word; report the changeset (updated / deprecated / new / deleted) by case number and title, never by id alone.
